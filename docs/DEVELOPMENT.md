# Building and testing

## Firmware toolchain

Install Python 3 and Arduino CLI on the development computer. From
`dragon-firmware`, run:

```sh
python tools/dev.py setup
python tools/dev.py build
python tools/dev.py ports
python tools/dev.py upload --port YOUR_PORT
python tools/dev.py monitor --port YOUR_PORT
```

On Windows, Python may be `py`; on Unix it may be `python3`. Use `--cli PATH`
if Arduino CLI is not on PATH. Setup installs Arduino-ESP32 3.2.1 and Adafruit
NeoPixel 1.12.5. The helper selects the ESP32-S3, USB hardware CDC, 4 MB flash,
2 MB PSRAM and custom partitions. It enforces the actual 0x180000-byte app
partition limit rather than trusting the compiler's generic flash percentage.

Do not upload to a port remembered from a prior session without checking its
current identity and wiring. Close monitors before uploading. Laptop USB and
external/main power must not be connected simultaneously in the present circuit.

## Editable sources

- Palette catalog: `presets/dragons.json`, generated by `tools/palettes.py`.
- Phone UI: `web/dragon-den.html` and `web/library.js`, embedded by
  `tools/embed_web.py` during every build.
- `DragonPresets.h` and `DragonWebPage.h` are generated and retained for
  inspecting the actual shipped code. Do not hand-edit them.
- `DragonPrototype/build_opt.h` must remain in the sketch so the network-event
  locking definition applies consistently to the networking libraries.

Catalog IDs depend on order. Preserve order or implement a saved-library
migration before changing it. Library snapshots are versioned binary records,
not cross-platform user backup files.

## Python and native regression checks

Use a C++17 compiler and Python with tkinter available:

```sh
python tools/run_tests.py
```

Use `--cxx PATH` for a compiler not on PATH, or `--zig PATH_TO_ZIG` for Zig's
C++ mode. The runner builds ten independent suites under ignored `.tools/`.
The editor Python test uses Tk and needs a display. On Linux headless runners,
install tkinter/Xvfb and run `xvfb-run -a python tools/run_tests.py`.

Native tests substitute sensor/serial/storage fakes and exclude the Wi-Fi radio
adapter. They verify firmware logic, not the physical circuit or Wi-Fi stack.

## Phone-browser simulations

From `dragon-firmware`, install Node.js dependencies and a browser:

```sh
npm install
npx playwright install chromium
npm run test:web
```

`tools/test_web.cjs` can also take a Playwright package path followed by an
optional browser executable. It has been run locally with a bundled Playwright
runtime and headless Edge. Tests use simulated HTTP responses at a 390×844
viewport; screenshots go to `.tools`. Do not present them as physical-phone
or ESP32 API verification.

## Prepared device and setup card

Install Python's `pyserial` for serial tools. Immediately after upload/reset:

```sh
python tools/capture_web_setup.py --port YOUR_PORT
```

This captures the boot setup line, writes local credentials and generates a
printable card under `.tools`. Its log redacts the password. Never commit the
card/credential capture. Parents should receive the card, not coding tools.

## Release checklist

1. Pass regression suites, browser simulations and firmware build.
2. Review generated headers for intentional source changes.
3. Validate staged files: no `.tools`, credentials, build products or large
   duplicate meshes/archives.
4. Record physical evidence separately from simulated checks.
5. Complete the actual-phone, persistence, touch-gesture and power checks in
   PROJECT-STATUS.md before a family release.
6. Review later STL, photos and Gerbers as a distinct hardware revision.
